# Branching Strategy Guide

---

## 1. Purpose

This guide defines the **standard Git branching strategy** for engineering projects: how branches are created, named, used, reviewed, merged, and retired.

It exists to prevent the problems that come from inconsistent Git practices as teams grow:

- Unclear branch responsibilities
- Poor traceability between code changes and tasks
- Increased merge conflicts
- Risk of unstable code reaching production
- Difficult repository maintenance

This guide is part of the [Development & Engineering Standards](Development--Index) module.

**Out of scope:** Git command reference documentation, Git installation instructions, repository-specific CI/CD configuration.

---

## 2. Branch Architecture

### 2.1 Protected Branches

Used for stable and integration code. Direct pushes are disallowed; changes land only via reviewed Pull Requests.

| Branch    | Purpose                                                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------- |
| `main`    | Always reflects the latest stable, production-ready code                                                |
| `stage`   | Staging branch; holds release-candidate code for pre-production verification before promotion to `main` |
| `develop` | Integration branch; latest state of work destined for the next release                                  |

### 2.2 Short-Lived Branches

Created for a single unit of work and removed once merged.

| Type    | Prefix     | Used for                                      |
| ------- | ---------- | --------------------------------------------- |
| Feature | `feature/` | New functionality                             |
| Bugfix  | `bugfix/`  | Bug fixes                                     |
| Release | `release/` | Stabilizing a release candidate before `main` |
| Hotfix  | `hotfix/`  | Urgent patches against production             |

---

## 3. Branch Naming Convention

Branch names must be consistent, ticket-traceable, and machine-parseable.

```
<type>/<issue-number>-<short-description>
```

- **type** - one of `feature`, `bugfix`, `release`, `hotfix`
- **issue-number** - the autogenerated issue number assigned when the ticket is created, so board automation and PM tooling can link branch → ticket
- **short-description** - lowercase, hyphen-separated, brief

**Examples:**

```
feature/014-branching-strategy-guide
bugfix/102-footer-email-domain
hotfix/003-checkout-500-error
release/2026.08.0
```

> [!NOTE]
> A branch with no issue number is a signal the work doesn't have an issue yet - see [Development Workflow §3.1](Development--Workflow).

## 4. Branch Lifecycle

### Task → Objective → Procedure → Result

**Objective:** every branch has a clear origin, a clear destination, and a defined end of life.

**Procedure:**

1. **Create from** - feature/bugfix branches are cut from `develop`; hotfix branches are cut from `main`
2. **Merge to** - feature/bugfix branches merge back into `develop`; hotfix branches merge into both `main` and `develop`; release branches merge into `main` (and are back-merged into `develop`)
3. **Remove when** - a branch is deleted immediately after its Pull Request is merged; long-lived local copies are not kept

**Result:** no branch outlives the work it represents, and history stays traceable from ticket → branch → PR → merge commit.

---

## 5. Pull Request & Review Process

- All changes reach a protected branch through a Pull Request - no direct pushes
- For reviewer expectations and the review process itself, see [Code Review & PR Guidelines](Development--Code-Review-And-PR-Guidelines).

---

## 6. Quality & Repository Standards

- **Required checks before merge:** CI must pass (lint, test, build) before a PR is mergeable
- **Merge practice:** squash noisy WIP commits before merging where the workflow allows it, so `develop`/`main` history reads cleanly - see [Commit Message Guidelines](https://github.com/liongate-sarl/liongate-docs/blob/main/Templates/COMMIT_MESSSAGE_TEMPLATE.md)
- **Branch cleanup:** merged branches are deleted from the remote immediately; stale unmerged branches are reviewed and pruned periodically

---

## 7. Why This Matters

Following this strategy improves:

- **Collaboration** - clear ownership per branch, no stepping on others' work
- **Code quality** - nothing reaches a protected branch without review and passing checks
- **Production stability** - `main` is always deployable; hotfixes have a defined, fast path
- **Repository maintainability** - no accumulation of stale or ambiguously-named branches

---

## 8. Risks

- **Risk:** developers may not consistently follow the defined workflow → **Mitigation:** enforce branch protection rules and required PR approvals at the repository settings level, not just in documentation
- **Risk:** the strategy may become outdated as team practices evolve → **Mitigation:** review and update this guide periodically, owned by Engineering
